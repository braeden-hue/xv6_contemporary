- 혼합 워크로드 실행·로그 검증·결과 집계 자동화
- 결과 수집 방식에 따른 실험 간섭 분석

> **시각 자료 배치:** 스케줄러 구조도
> 사용자 워크로드, 커널 진입, `dispatch<P>()`, 정책 선택의 관계를 먼저 보여준다.

## 2. Episode 1 — Policy Abstraction with Modern C++

### 설계 질문

**스케줄러의 공통 처리를 유지하면서 정책을 교체할 수 있는가? 그리고 선택한 추상화 방식에는 어떤 실행 비용이 있는가?**

정책을 바꿀 때마다 잠금·프로세스 상태 전환·문맥 교환 코드를 함께 수정하지 않도록, 공통 실행 구조와 정책 결정을 분리했다.

### 구현 구조

정책은 두 인터페이스를 제공한다.

```cpp
pick_next()       // 다음 실행 작업 선택
should_preempt()  // 현재 작업의 CPU 양보 여부 판단
```

`SchedulerPolicy` concept으로 인터페이스를 검사하고, 공통 `dispatch<P>()`에 정책을 템플릿 인자로 결합한다. 활성 정책은 컴파일타임에 선택한다.

```cpp
template<typename P>
concept SchedulerPolicy = requires(P policy, struct proc* procs, int n, struct proc* running) {
    { policy.pick_next(procs, n) } -> std::same_as<struct proc*>;
    { policy.should_preempt(running) } -> std::same_as<bool>;
};

template<SchedulerPolicy P>
[[noreturn]] static void dispatch(P& policy)
{
    ...
    struct proc* next = policy.pick_next(proc, NPROC);
    ...
}

using ActivePolicy = PriorityPreempt<true>;
```

정책 선택은 런타임 가상 인터페이스가 아니라 컴파일타임에 고정된다 — 빌드된 커널의 심볼 테이블에는 활성 정책이 아닌 정책의 코드가 존재하지 않는다. RR, FCFS, `PriorityPreempt<UseCounter>`가 별도 정책 타입으로 구현되어 있으며, CFS는 설계만 하고 보류했다.

이 구조는 이후 정책 비교에서 **공통 실행 경로를 유지하고 정책 결정 부분을 교체하는 기반**이 된다. 커널은 예외·RTTI·hosted C++ 런타임을 가정하지 않는 freestanding 환경을 유지한다.

### 호출 비용 비교

동일한 C++ 벤치마크에서 정적 템플릿 호출과 함수 포인터 호출을 비교했다(`CPUS=1`, `-icount shift=0` 결정론적 명령어 계수 환경).

| 측정 항목 | 결과 |
|---|---:|
| Trivial static 호출당 비용 | 2 instret |
| Trivial function-pointer 호출당 비용 | 14 instret |
| 두 호출 경로의 차이 | 12 instret |
| NPROC opaque 조건의 RR static–fnptr 차이 | 15 instret |

**관찰:** 해당 벤치마크 조건에서 정적 템플릿 방식이 함수 포인터 방식보다 적은 명령어를 사용했다.

초기 RR 본문 측정에서는 오히려 static 버전이 함수 포인터 버전보다 174 instret 더 많이 소비하는 역전 현상이 있었다. 디스어셈블리로 추적한 결과, 인라이닝이 컴파일타임 상수인 `NPROC=64`를 컴파일러에 노출시켜 `% 64` 연산이 소프트웨어 명령어 시퀀스로 강도 축소(strength-reduction)된 반면, 함수 포인터 버전은 그 상수를 보지 못해 하드웨어 `remw` 한 명령으로 처리되어 우연히 앞선 것이었다. 프로세스 수를 `volatile`로 불투명화해 이 역전을 제거하고 나서야 순수 호출 경로 비용만 분리할 수 있었다.

**해석 범위:** 원본 xv6 C 스케줄러와의 직접 비교는 수행하지 않았다. 따라서 C 대비 성능 개선, 추상화 없는 구현과의 동등성, 추가 비용 0을 입증한 결과로 해석하지 않는다. 함수 포인터 결과를 모든 `virtual` 호출의 비용으로 일반화하지도 않는다. (이 gap을 좁히기 위한 원본 `scheduler()` vs 현재 `RR::pick_next()` 직접 대조 벤치마크를 설계했으며, 아직 구현·실행 전이다.)

> **Episode 1의 결과:** 정책 비교를 위한 공통 구조를 구축하고, 선택한 호출 방식의 비용을 제한된 조건에서 검증했다.

## 3. Episode 2 — Scheduling Policy Comparison

### 연구 질문

**짧은 작업을 우선 처리하면 응답시간이 줄어드는가? 그 대가로 전체 완료 시간과 긴 작업의 지연은 얼마나 증가하는가?**

short task 10개와 long task 2개를 고정된 도착 스케줄로 실행하고, 동일한 C++ 실행 구조에서 세 정책을 비교했다.

| 정책 | 선택 기준 | 사용자 모드 타이머 tick에서 |
|---|---|---|
| RR | RUNNABLE 작업 순환 선택 | 항상 양보 |
| SelectOnly | LatencySensitive 작업 우선 | 항상 양보 |
| Preempt | SelectOnly와 동일 | LatencySensitive 실행 유지 |

short 여부는 작업이 미리 선언한다. 실행 이력으로 작업 길이를 추정하는 정책은 이번 실험에 포함하지 않았다.

### 측정 방법

- **응답시간:** release → 사용자 코드 실행 재개
- **Makespan:** 공통 시작점 → 가장 늦은 작업 본문 완료
- **Long 완료 지연:** 각 long 작업의 release → 본문 완료
- **대기 지표:** 최대 runnable 대기시간
- **실험 유효성:** 레코드 정합성과 release jitter

> **시각 자료 배치:** 혼합 워크로드 타임라인
> 도착·응답 대기·본문 경과 시간을 구분한다. 본문 경과 구간을 순수 CPU 점유 시간으로 표시하지 않는다.

### Stage A — 계측의 구조적 검증

정책 비교 전에 회귀 테스트와 RR 파일럿 2회를 수행했다. 레코드 누락·중복과 집계기 finding은 없었다.

두 실행 모두 short 응답 median **2 tick**, max **3 tick**, makespan **58 tick**이었다.

이는 정책 비교를 진행하기 위한 구조적 정합성 확인이다. 측정 간섭이 없음을 보장하는 결과는 아니다.

### Stage B — 응답 개선과 완료 지연

커널 재빌드 누락을 수정하고 정책별 바이너리 대응을 확인한 뒤, **5라운드 × 3정책**을 재실행했다.

| 평가 항목 | SelectOnly | Preempt |
|---|---:|---:|
| Short median ≥1 tick 개선 | 5/5 | 5/5 |
| Short max 방어 | 5/5 | 5/5 |
| Makespan ≤RR의 1.10배 | 1/5 | 1/5 |
| Long D0 ≤RR의 1.25배 | 4/5 | 4/5 |
| Long D6 ≤RR의 1.25배 | 4/5 | 4/5 |
| 종합 목표 | 미달 | 미달 |

두 정책 모두 short 응답 median이 **2→1 tick**으로 감소했다. 그러나 완료 지연 기준은 모든 라운드에서 만족하지 못했다. 큰 지연이 관측된 실행도 제외하지 않았다.

> **시각 자료 배치:** *Preliminary policy comparison*
> 응답 개선과 완료 지연을 함께 제시하고, 반복별 변동을 보존한다.

### Stage C — 측정 과정도 다른 작업을 지연시키는가?

작업 본문이 끝난 뒤의 결과 수집도 다른 작업의 실행을 방해할 수 있었다. 공유 파일 수집에서 큰 release jitter를 관찰했고, 수집 전 우선순위 하향으로 정상 범위에 돌아오는 현상을 확인했다.

이후 세 수집 조건을 **5라운드 × 3정책 × 3조건, 총 45회** 비교했다.

| 조건 | 수집 방식 |
|---|---|
| V | 기존 즉시 콘솔 출력 |
| VD | 우선순위 하향 후 즉시 출력 |
| QD | 우선순위 하향 후 파이프 전달·회수 후 출력 |

45회 중 V 실행 1건에서 콘솔 레코드 손상을 발견했다. 해당 실행은 보존하고 필요한 대조만 결측 처리했다.

수집 조건 간 short 응답 median·max 차이는 관측되지 않았다. 다른 지표의 중앙값 차이는 작았지만 일부 라운드에는 큰 변동이 남았다. 이를 특정 syscall의 비용이나 확정된 원인으로 해석하지 않았다.

> **시각 자료 배치:** *Measurement interference: paired collection-mode comparison*
> 개별 라운드를 연결하고, 손상된 실행은 결측으로 표시한다.

### icount — 보조 재현성 확인

일반 TCG와 분리해 QD 조건에서 정책별 3회씩 실행했다. 9회 모두 구조 검사와 도착 조건을 만족했고, 정책별 지표는 세 반복에서 동일했다.

| 지표 | RR | SelectOnly·Preempt |
|---|---:|---:|
| Short 응답 median / max | 2 / 3 | 1 / 1 |
| Makespan | 74 | 80 |
| Long D0 / D6 | 65 / 56 | 73 / 61 |

응답 개선과 완료 지연 증가의 방향은 같았다. 다만 makespan 증가율 **8.1%**, long 지연 증가율 **12.3%·8.9%**는 기존 참고 한계 안에 있었다.

시간 진행 조건에 따라 비용의 크기와 기준 충족 여부가 달라졌으므로, 일반 TCG와 합산하거나 Stage B의 판정을 대체하지 않았다.

## 5. 결론과 후속 연구

**Episode 1**에서는 Modern C++로 정책을 분리하고, 정적 템플릿 호출이 함수 포인터 호출보다 적은 명령어를 사용하는 조건을 확인했다.

**Episode 2**에서는 우선순위 정책의 short 응답 개선과 완료 지연 증가를 관찰했다. 또한 결과 수집과 시간 진행 조건이 성능 평가에 영향을 줄 수 있음을 확인했다.

현재 결과는 단일 코어 QEMU와 작은 고정 워크로드의 tick 단위 실험이다. 실제 데이터센터나 microsecond-scale 성능으로 일반화하지 않는다.

후속 연구 질문은 다음과 같다.

- Budget·aging으로 응답 개선을 유지하면서 긴 작업 지연을 제한할 수 있는가?
- 실행 이력 기반 작업 분류가 명시적 우선순위 선언을 대신할 수 있는가?
- 더 짧은 시간 규모에서 평가하려면 어떤 실행 환경과 계측이 필요한가?

이 프로젝트를 통해 **정책 추상화 구현, 비용 분리 실험, 계측 오류 진단, 재현 가능한 성능 평가**를 경험했으며, 이를 바탕으로 스케줄링과 저지연 시스템 연구를 발전시키고자 한다.

## 6. 실행 방법

빌드는 GCC 14 RISC-V 크로스 툴체인과 C++23 커널 소스 기준으로 구성되어 있다. C++ 파일은 `-ffreestanding`, `-fno-exceptions`, `-fno-rtti`를 포함한 freestanding 제약으로 컴파일된다.

요구 사항:

- RISC-V GCC/G++ 14 크로스 툴체인
- QEMU >= 7.2

xv6 실행:

```bash
make qemu
```

스케줄러 계측 회귀 테스트(xv6 내부에서):

```
$ usertests -q
$ statstest
```

C++ 커널 파일에 대한 GCC 정적 분석:

```bash
make analyze
```

Makefile은 위 벤치마크에 사용한 디스어셈블리·심볼 파일도 함께 생성한다. Episode 2의 원시 로그·집계 스크립트·manifest는 [`docs/bench/`](docs/bench/)에 보존되어 있다.
